What access do we need — and why?

Magrabi + DoctorM · Production and separate UAT credentials · UAE / Saudi Arabia / Egypt / Qatar / Kuwait · Reviewed 14 October 2026

Feasible, with conditions — not ready simply by collecting logins. Existing data and documented APIs support the design. Merchant entitlements, hosted service-account permissions, data completeness and production tracing must still pass the checks below. This document does not claim those grants are already present, and no access or production configuration has been changed.
Human login ≠ automated data accessNamed viewer access helps validate totals. Scheduled collection needs a dedicated API identity or approved reporting feed.
Prefer existing verified feedsReuse order records and verified payment events. Do not replace payment callbacks or expose merchant keys to the dashboard.
Access alone cannot create missing dataThe complete funnel and trace journey need instrumentation. Missing historical events or dropped logs cannot be recovered from a new token.

Definition of “connected”: approved scope + successful least-privilege read from the hosted service + field/history/coverage validation + reconciliation to source totals. A portal login, API documentation or a green connection test alone does not meet this definition.

4. Exact handoff requested from each owner

One inventory row per account / merchant / source

  1. System and named owner; production and UAT kept separate.
  2. Brand, country/channel, legal entity, merchant/store/processing-channel or property/project ID; currency.
  3. Supported API/reporting URL and documentation; allowed operations and authentication type.
  4. Service-account identifier and secure vault reference; expiry, rotation owner and network allowlist.
  5. Available date history, pagination, rate limits, refresh delay, log quota and field completeness.
  6. Sanitized example response and agreed IDs for reconciliation; a named person to validate totals.

Permissions not required for reporting

  • No payment authorize/capture/refund/void operations.
  • No production order changes, DB superuser, write access to source databases, pod restarts or cluster-admin role.
  • No Apple .p8/B2C authentication secrets.
  • No personal/shared admin passwords in browser code, reports or exported files.
  • No full request/response bodies by default. Safe allowlisted context only, subject to privacy approval.

Owner-only setup actions—creating an identity, granting permissions, enabling diagnostics or releasing instrumentation—remain separately approved changes.

Start with: A1–A2 orders/OMS, A8–A10 technical telemetry and A18 platform. In parallel, payment owners validate A3–A7 and developers plan A11/A13. Add A16–A17 alerts once denominators and source freshness are reliable; A14–A15 are optional enrichment.
