3. Rules that keep the numbers trustworthy

Business definitions

  • Approve one canonical placed-order definition using Saleor creation events; show OMS receipt and business status separately so an OMS delay cannot look like missing storefront orders. Show gross placed, cancelled and net orders separately.
  • Compare equal completed hours in the selected timezone. Previous day and previous four same weekdays need enough retained history.
  • Keep AED, SAR, EGP, QAR and KWD separate. Only combine money with an approved FX policy and visible rate date.
  • Deduplicate attempts and callbacks. Payment-request events are not necessarily unique customers or completed payments.
  • Use cohort-based journey conversion. Historical order totals and surviving checkout rows cannot form a valid user funnel.

Technical & privacy boundaries

  • Front Door, CDN, ingress and gateway are separate counting layers; never add them into a single request total.
  • Missing, capped, late and sampled data must say so. Never turn unavailable logs into zero errors.
  • HTTP 200 can contain GraphQL errors or a payment requiring further action. Track transport and business outcomes separately.
  • Safe drill-down includes method, templated path, status, latency and correlation IDs. Bodies are allowlisted/redacted only when captured lawfully; historical payloads cannot be invented.
  • Never record credentials, cookies, payment-card details or unrestricted customer data. Apply retention, access control and audit logs.

4. Implementation ownership and delivery sequence

DevOps / platform

  1. Inventory source permissions, retention, log quotas and existing alerts.
  2. Provide server-only reader identities and approved API connectivity; build bounded collectors, caches and source-health checks.
  3. Expose traffic/error and infrastructure panels; preserve per-source scope.
  4. Host the approved backend/UI and configure monitored Teams/email delivery, RBAC and audit retention.

Developers / business / analytics

  1. Approve canonical order, payment, country and baseline definitions with business owners.
  2. Provide stable OMS/Saleor feeds and verified gateway state mapping.
  3. Instrument each browser journey step and backend confirmation; add trace propagation and safe application error context.
  4. Validate with known transactions, cancellations, retries and feed outages; approve thresholds and rollout.

Suggested sequence: definitions & access → orders/payments/technical overview → journey & tracing → optional UX/GA4. A delivery estimate should follow this access and instrumentation review; no unverified date or effort promise is included.

5. Where the sources live

  • Existing portal insights — integration location, not a claim this proposed dashboard is already deployed.
  • ECom Grafana — existing Loki/Prometheus access point; use scoped server-side readers.
  • Main Front Door metrics · Separate ECom CDN metrics · Macula gateway metrics — verified resource names from the local traffic source catalog.
  • OMS/Saleor: approved private read-only APIs/database views, not a database connection embedded in the HTML. Final endpoint, service identity and permissions must be agreed with owners.
  • Sentry, payment providers, Clarity and GA4: project/provider-specific read scopes, identifiers and integration permissions must be confirmed; no credentials are included here.

6. Product limits checked against official guidance

  • Azure Front Door monitoring: diagnostic logs have processing delay and must be enabled; access/WAF records can be correlated using the tracking reference.
  • Azure WAF monitoring: WAF records describe matching security rules, not all customer requests. Multiple matches require careful counting.
  • Clarity export API: 10 requests per project/day, previous 1–3 days, up to 1,000 rows with no pagination. Use scheduled cached summaries, not a live per-refresh feed.
  • GA4 data freshness: standard intraday reporting is typically 2–6 hours; realtime is narrower. Keep operational order monitoring independent.
