10. Metrics and correctness contract

Make misleading numbers impossible by design

  • Orders: count unique agreed parent/canonical orders. Show placed in Saleor, received by OMS, cancelled and net orders separately. Do not sum Saleor and OMS orders or treat an OMS delay as absence of storefront orders.
  • Comparisons: previous day, approved benchmark and average of previous four same weekdays. Use equal elapsed/completed hours in the chosen timezone. Store timestamps in UTC; display IST/Dubai or selected timezone explicitly.
  • History: retain selected reporting range plus at least 28 preceding days for four-week weekday comparison, with ingestion-lag margin. Current traffic collector is seven days per run within a 93-day horizon; source retention may be shorter.
  • Countries/currencies: UAE, Saudi Arabia, Egypt, Qatar and Kuwait from approved order/channel mapping. Keep AED, SAR, EGP, QAR and KWD separate unless business approves an FX rule. IP geography is not order country.
  • Payments: deduplicate attempts and callbacks by stable IDs; initiated/action-required/authorized/captured/failed/refunded are distinct. Approve the denominator for each rate. HTTP 200 or AUTHORIZATION_ACTION_REQUIRED is not payment success.
  • Journey: count defined users/sessions/cohorts across events. Surviving checkout rows cannot reconstruct completed journeys because checkouts may disappear when orders are created. Historical events cannot be invented.
  • Traffic: keep main Front Door, separate CDN, ingress, filtered storefront and Macula gateway totals separate. Never add overlapping layers or aggregate rows plus their detail. Macula ResponseStatus groups mean 2xx, not exact 200.
  • Bots/customers: separate known monitoring, internal/scripts, declared crawlers, browser-like and unknown traffic. Filtered traffic is a customer-facing proxy, not verified humans. WAF rule matches must be deduplicated before counting requests.
  • Errors: final HTTP status and upstream retries are separate. Track GraphQL errors and business outcomes alongside transport codes. Drill-down includes allowlisted method, templated path, status, latency and correlation IDs; never raw tokens, cookies, card data or unrestricted bodies.
  • Freshness: show source, time window, timezone, collected time, source watermark, lag, retention and completeness. Missing/capped/sampled data is unavailable or partial, never zero. A green connection test does not prove data completeness.

Suggested normalized records: source identity/brand/channel/country; order and external-order IDs; payment attempt/provider reference; event_time/received_time/updated_at; lifecycle state; currency/amount; request_id/trace_id; schema version. Keep join keys server-side and pseudonymize client-facing identifiers where required.

13. Live release and rollback checklist

For the later approved release, not an instruction to deploy now

  • Record the approved commit, image digest, config/schema versions and expected resource changes. Diff against the current live image and configuration again immediately before release.
  • Check the live portal for active deployment runs through approved read-only mechanisms. If visibility is unavailable, stop; do not infer inactivity. A portal restart can interrupt its deployment workers.
  • Confirm current capacity, independent backups, reporting-store migration reversibility, session handling and least-privilege identities. Do not copy local Key Rotation/synthetic work into the release unintentionally.
  • Present exact Azure/Kubernetes or pipeline actions for approval. Keep namespace, resource names and image digest explicit. Use the existing change/release approvals; no blanket portal or cluster access.
  • Deploy only the reviewed changes. Verify readiness, login, permissions, old portal functions, new data-source checks, source reconciliation, navigation across both frontend builds and healthy collector resource use.
  • Production alerts start with agreed destinations and thresholds; test destinations never silently become production notifications. All alert rules have an owner, cooldown and recovery action.
  • Rollback must restore the captured previous image/config, not an arbitrary previous revision. Pause only the new collectors/alerts through their approved controls; preserve checkpoints and reporting data for reconciliation.
  • Database migrations need a separately reviewed rollback/forward-fix plan. Do not delete analytics data or restore a production database as an automatic portal rollback.
